# Миграции Urfu_Practices — обновлённый MVP

Комплект предназначен для **новой пустой БД PostgreSQL 15+**. Это начальное создание схемы, а не перенос данных из предыдущей версии. Применять этот комплект вместе со старой начальной миграцией нельзя: они создают одноимённые таблицы разных моделей.

Источник — `Схема БД/Аналитика_2_БД_только_MVP.drawio`, страницы «Схема базы данных» и «Правила БД», редакция **16.11.2026**. SHA-256 исходного файла:

```text
9472AA03936FC8A7EDFCF707B5877944BDC1FCC47A3F4C4A992C74DD3EF42217
```

В модели **4 таблицы, 42 поля и 8 внешних ключей**:

| Таблица | Назначение |
| --- | --- |
| `users` | Пользователи, роли и группа студента |
| `groups` | Курсы-группы, сроки и куратор |
| `assignments` | Задания/отчёты, черновики, публикация и получатель |
| `submissions` | Единственная сдача студента, один файл и результат проверки |

Все четыре `id` имеют тип `integer GENERATED ALWAYS AS IDENTITY`; все внешние ключи — `integer`. **Обновлённая схема имеет приоритет над старым API-контрактом с UUID.** Для подключения бэкенда следует обновить контракт и типы идентификаторов в Go/клиенте; смешивать UUID и новые числовые ID нельзя.

Файл хранится непосредственно в `submissions.file_data` типа `bytea`. Отдельных таблиц файлов и оценок нет. `UNIQUE (assignment_id, student_id)` разрешает ровно одну сдачу студента по заданию. Повторной отправки, замены файла и истории попыток в этой редакции нет; решение `revision_required` само по себе не разрешает пересдачу.

## Состав комплекта

| Файл | Назначение |
| --- | --- |
| `migrations/000001_init_mvp.up.sql` | Создание новой схемы |
| `migrations/000001_init_mvp.down.sql` | Откат с удалением созданных таблиц и их данных |
| `migrations/verify.sql` | Проверка структуры без изменения данных |
| `tests/migrations.cjs` | Изолированные интеграционные проверки SQL |
| `tests/schema.expected.json` | Поля, типы и NULL, извлечённые из исходного drawio |
| `schema/Аналитика_2_БД_только_MVP.drawio` | Актуальная схема для бэкенд-разработчика |

В исходном рабочем каталоге старые файлы `migrations/` сохранены отдельно от этого комплекта. Для новой установки выбрать только комплект обновлённого MVP. Если используется инструмент управления миграциями, в его каталоге должна находиться только выбранная цепочка миграций.

## Запуск через Docker

Команды ниже выполняются в **PowerShell из корня распакованного комплекта**, где находятся этот README и папка `migrations/`. Docker Desktop должен быть запущен. Файл Compose берётся из исходного проекта `Urfu_Practices-main`; указать его фактический абсолютный путь:

```powershell
$composeFile = 'C:/путь/к/Urfu_Practices-main/docker/docker-compose.yml'
docker compose -f $composeFile up -d postgres
docker compose -f $composeFile exec -T postgres pg_isready -U dev_user -d internship_db
```

Дождаться ответа `accepting connections`. Используются имена сервиса, пользователя и БД из предоставленного архива: `postgres`, `dev_user`, `internship_db`. Целевая БД должна быть новой и пустой. Запуск контейнера с ранее использованным томом сам по себе не очищает БД.

Применить начальную миграцию:

```powershell
docker compose -f $composeFile cp ./migrations/000001_init_mvp.up.sql postgres:/tmp/000001_init_mvp.up.sql
docker compose -f $composeFile exec -T postgres psql -U dev_user -d internship_db -v ON_ERROR_STOP=1 -f /tmp/000001_init_mvp.up.sql
```

Проверить структуру:

```powershell
docker compose -f $composeFile cp ./migrations/verify.sql postgres:/tmp/verify.sql
docker compose -f $composeFile exec -T postgres psql -U dev_user -d internship_db -v ON_ERROR_STOP=1 -f /tmp/verify.sql
```

`ON_ERROR_STOP=1` завершает psql при первой ошибке. Это одноразовый запуск начальной миграции; существующую схему не следует повторно создавать поверх прежней. Ручной запуск через psql не ведёт журнал версий миграций.

`verify.sql` сверяет поля, типы, NULL, IDENTITY, выражения DEFAULT, внешние ключи, первичные/уникальные ключи и обязательные индексы. Для DEFAULT проверяются точные выражения восьми значений из начальной миграции и отсутствие дополнительных значений у других полей. Выражения читаются из метаданных без выполнения. Для CHECK проверяются наличие именованных ограничений и признак их валидации; определения выводятся в отчёте для просмотра. При расхождении скрипт выдаёт ошибку `P0001` с именем поля или объекта.

## Что обеспечивает SQL

- Четыре таблицы с типами и обязательностью полей обновлённой модели, автоматически выдаваемые числовые ID и восемь FK с `ON DELETE RESTRICT ON UPDATE RESTRICT`.
- Уникальность логина и email без учёта регистра и пробелов по краям через `lower(btrim(...))`; обязательность непустых значений. Вход должен использовать ту же политику сравнения.
- Допустимые роли и согласованность `users.group_id`: у студента группа обязательна, у куратора и администратора — отсутствует.
- Корректный порядок дат группы; допустимые типы/статусы задания, не более одного получателя и обязательные данные публикации.
- Наличие хотя бы одного непробельного символа в имени пользователя, имени группы, названии и обязательных текстах задания, имени/MIME файла и обязательном комментарии к доработке. Табуляция и переводы строк сами по себе содержимым не считаются. Форматирование вокруг содержательного текста допускается.
- Единственную сдачу на пару задания и студента; обязательный файл размером от 1 до **20 000 000 байт**, совпадение `size_bytes` с фактической длиной `file_data`, непустые имя и MIME.
- Неотрицательный целочисленный балл, допустимое решение и согласованность полей результата с текущим статусом сдачи. Нулевой балл отличается от отсутствующего `NULL`.
- Временную согласованность внутри строк: публикация задания после создания, проверка после отправки, публикация результата после проверки.
- Индексы выборок и внешних ключей, перечисленные в схеме; отдельный индекс или уникальность на содержимом файла не создаются. Одинаковые байты в разных сдачах допустимы.

Проверка текущего состояния строки не заменяет проверку допустимости изменения: SQL-ограничение может разрешать два состояния по отдельности, а сервис обязан запретить недопустимый переход между ними.

## Что остаётся Go-бэкенду

1. **Авторизация и доступ.** Проверять права при каждом чтении и изменении. Студент получает только свои задания/работы; куратор — разрешённые группы/сдачи. До публикации не отдавать студенту подготовленные `score`, `feedback`, `decision` и не включать их в расчёты.
2. **Роли и связи.** FK подтверждает существование пользователя, но не роль. Проверять кураторов, студента-получателя, автора сдачи, принадлежность группе и активность пользователей. При отправке сервер назначает `submissions.curator_id` по группе студента; клиент не выбирает проверяющего.
3. **Процесс работы.** Проверять публикацию задания, получателя и дедлайн до отправки. Обеспечивать переходы `submitted → under_review → graded/revision_required`. Публикацию результата и итоговый статус устанавливать одним UPDATE. Запрещать повторную отправку, замену отправленного файла и изменение опубликованного результата.
4. **Изменение связанных данных.** После публикации не менять получателя задания; после первой сдачи не менять его `type`. До согласования отдельной процедуры блокировать изменения роли, группы студента и куратора группы при связанных учебных данных. Деактивация не должна оставлять действующую группу или незавершённую проверку без активного куратора.
5. **Содержимое файла.** Проверять PDF, DOCX или ZIP по фактическим байтам, а не только по расширению/MIME браузера. Сохранять файл и метаданные атомарно. В списках выбирать явные поля без `file_data`; получать байты отдельным запросом после проверки доступа. Не выполнять `SELECT *` для списков сдач.
6. **Ввод и учётные данные.** Нормализовать логин/email по согласованной политике, хешировать и проверять пароль, валидировать целочисленность балла до записи. Поле `integer` не заменяет валидацию JSON: явное приведение дробного numeric в PostgreSQL может округлить значение.
7. **Решения API.** Определить приём работ после дедлайна, формулу среднего, округление, учёт несданных/возвращённых работ и временный механизм входа. События передавать в ISO 8601 с UTC/смещением; тип `timestamptz` сохраняет момент времени, а отображение зависит от часового пояса сеанса.

## Откат

**Обычный rollback удаляет таблицы этого комплекта вместе со всеми их данными, включая файлы в `bytea`.** Он не возвращает старую модель и не восстанавливает удалённые данные. Для рабочей БД предварительно необходима проверенная резервная копия.

Из корня распакованного комплекта с уже заданной переменной `$composeFile`:

```powershell
docker compose -f $composeFile cp ./migrations/000001_init_mvp.down.sql postgres:/tmp/000001_init_mvp.down.sql
docker compose -f $composeFile exec -T postgres psql -U dev_user -d internship_db -v ON_ERROR_STOP=1 -f /tmp/000001_init_mvp.down.sql
```

После отката структуру можно создать заново через up; данные восстанавливаются только из резервной копии. При дальнейшем изменении требований обновлять диаграмму и добавлять новую версию миграции, а не переписывать уже применённую версию.

## Проверка комплекта

19.11.2026 успешно выполнены **402 интеграционные проверки** в изолированной PGlite 0.5.15 (PostgreSQL 18.6, WebAssembly). Проверены:

- Точное совпадение всех 42 полей, типов и NULL с полями таблиц drawio; четыре ALWAYS IDENTITY, восемь FK и их RESTRICT.
- Уникальность логина/email с разным регистром и пробелами, роли и группа, черновики и условия публикации. Для обязательных текстов дополнительно проверены табуляция, переводы строк и содержательный текст с форматированием.
- Единственная сдача, сохранность бинарных байтов, соответствие размера файлу, фактические файлы размером 1, 20 000 000 и 20 000 001 байт.
- Все **256 сочетаний** статуса, решения и заполненности полей результата, включая опасные случаи NULL; нулевой балл, подготовка и публикация результата.
- Отказ повторной сдачи после обоих итоговых решений, ограничения удаления, отказ повторного up, удаление identity-последовательностей и повторный цикл up/down.
- Проверочный SQL выдаёт ошибку на прежней шеститабличной UUID-схеме, при удалении или отсутствии валидации проверок размера файла, изменении типа/NULL/IDENTITY, цели FK, индекса либо удалении уникальности сдачи.
- Для каждого из восьми DEFAULT проверены удаление и замена выражения. Дополнительно проверены ошибочный DEFAULT балла и подмена обычного поля вычисляемым столбцом.
- Ошибка отката на таблице groups после выполнения предыдущих DROP восстанавливает таблицы, данные сдач и users_group_fk одной транзакцией.
- SHA-256 приложенной схемы совпадает с исходным файлом и манифестом тестов.

Синтаксис рассчитан на PostgreSQL 15. Непосредственно контейнер PostgreSQL 15 из проекта не запускался: в окружении подготовки отсутствуют Docker/psql. Проверки API, прав доступа и реального содержимого PDF/DOCX/ZIP относятся к бэкенду и этими SQL-тестами не подтверждаются. Размер/трафик будущей БД не предоставлены; это создание новой схемы, без backfill существующих данных.

Для повторения тестов нужен Node.js. Из корня распакованного комплекта в PowerShell:

```powershell
npm install --prefix ./test-runtime --no-audit --no-fund --ignore-scripts @electric-sql/pglite@0.5.15
$env:PGLITE_MODULE = Join-Path $PWD.Path 'test-runtime/node_modules/@electric-sql/pglite'
node ./tests/migrations.cjs
```

Тесты работают в отдельной БД в памяти и не подключаются к `internship_db`. После успешного запуска выводится `result: passed` и число проверок.

Использованные возможности PostgreSQL 15: [IDENTITY и ограничения CREATE TABLE](https://www.postgresql.org/docs/15/sql-createtable.html), [уникальные индексы выражений](https://www.postgresql.org/docs/15/indexes-expressional.html), [octet_length для bytea](https://www.postgresql.org/docs/15/functions-binarystring.html), [метаданные DEFAULT и pg_get_expr](https://www.postgresql.org/docs/15/catalog-pg-attrdef.html).
